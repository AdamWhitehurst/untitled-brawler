Architecture review: the voxel map engine

untitled-brawler · 2026-10-20 · scope: crates/voxel_map_engine and its consumers in server, client, protocol, nostr_map_persistence

module seam leak across a seam deep module implementation hidden behind an interface

One root cause. No module owns a Map Instance's state, and I think every other complaint about this crate traces back to that. The state sits on 1 struct with 10 pub fields, 8 more structs the engine inserts a frame later, 2 structs the server must insert, and 1 system-local cache. Nothing can enforce an invariant, so invariants live in Query tuples, debug_assert!s and consumer discipline, and lib.rs exports all of it through a glob prelude. The algorithms (propagator, palette, greedy meshing, raycast, noise terrain) are deep and I would not touch them. The mud is the glue: lifecycle.rs, generation.rs, config.rs, instance.rs, persistence/.

No CONTEXT.md or ADRs exist. I took the domain nouns below from the code: Map Instance, Chunk, Column, Chunk Ticket, Chunk Envelope, Overworld, Homebase.

Two adapters would make the seam real, a filesystem store in production and an in-memory store in tests. Today every persistence test hits disk via tempfile.

problem
The engine's save path is half built. It knows how to queue, but it needs the server to supply the store, build envelopes, drain by hand and classify tombstones. The Store<K,V> seam has one adapter per type and binds to the filesystem adapter concretely anyway, so it pays the full cost of the generics and returns no leverage.
solution
Merge the two filesystem stores into one. Give the Map Instance flush_dirty, take_content_dirty and classify_for_publish; give the envelope a single encode/decode. Build storage from the already-present VoxelMapConfig.save_dir. Keep MapMeta and the change-set store on the server.
wins
  • locality: 5 envelope builders become 1
  • locality: tombstone race fixed where it lives
  • one codec, one zstd level
  • two adapters justify the seam
  • persistence tests run in memory
  • ~150 lines leave the server

Deletion test. Delete PendingSaves today and five near-identical copies remain in callers. After the move, deleting it removes them. Concentrates.

problem
The rules that decide what happens to a chunk next are spread across decision, execution, completion and enum, so understanding "a chunk gets loaded" takes 14 hops through 12 files and a minimum of 4 frames. The only tests are wall-clock dependent integration loops, and they assert on chunk_levels.len().
solution
Extract plan and apply as pure functions. generation.rs folds into the spawner. Systems become thin loops: plan, spawn, poll, apply.
wins
  • locality: stage rules in one place
  • tests become tables instead of frame loops
  • interface: two fns replace four files' worth
  • the 4-frame minimum becomes visible and tunable

Deletion test. The rules exist regardless. Today task plumbing interleaves them. Concentrated, the plumbing becomes a pass-through you could swap. Concentrates.

follow-up investigation · what a full read of the two ranges showed

The decision is already pure. Every stage rule reads only six facts: chunk status, fill type, effective level, column loaded, in flight, in bounds. Budget, in-flight cap, per-frame cap and terrain batching are loop control. They decide whether to continue, never which step a chunk gets. The disk-load attempt lives inside the async task (generation.rs:60-90), so plan never sees it. 14 of about 18 rules become table tests. apply needs only &mut VoxelMapInstance; mesh and entity spawning come back as returned instructions for the system to materialize.

No dependency on candidate 1. plan takes a value snapshot and apply reads fields already on the instance. The merge would shorten a 9-argument system signature and nothing more. This candidate can go first, and I would consider it, because its tests would catch regressions from the other three.

latent bugs the table exposed
lifecycle.rs:690-696 the loop pops a work item, then breaks on a cap. The popped chunk is dropped and nothing re-enqueues it.
lifecycle.rs:929-934 Terrain/Mesh results are inserted into the octree with no check that the column is still loaded; the Features path has that guard (:941), this one does not. Orphaned chunks never get cleaned up.
generation.rs:65-74 + lifecycle.rs:962-989 a disk hit builds a mesh for any mixed chunk regardless of saved stage, and completion spawns a mesh entity without dedup; a chunk saved at Terrain gets two mesh entities.
lifecycle.rs:721-724 stage cap uses the level snapshotted at enqueue time, not the live level.

The biggest risk is behaviour drift during extraction. Decide up front whether the dropped-on-break item and the snapshot-level cap are bugs to fix or behaviour to preserve, pin the choice as a table row, and land the extraction with current semantics before fixing either in a separate commit.

Delete outright, no design needed

  • mesh_cache.rs. Nothing in src/ references it, and ChunkData.hash goes stale after set_voxel, so a hash-keyed cache would serve wrong meshes
  • LoadState in ticket.rs has no reader
  • seed_from_id is the identity function
  • the tick Local in update_chunks is incremented and never read
  • the engine never reads VoxelMapConfig.{seed, generation_version, spawning_distance}, yet new asserts on one of them
  • VoxelChunk.lod_level is always 0
  • ChunkTicket::player doc says radius 200, code says 4
  • examples insert PendingChunks::default() by hand, which the engine also inserts
  • the glob prelude. Once 1 to 3 land, export the interface by name

Deep already, leave alone

propagator.rs (pure, 15 tests; only relocate its two constants) · palette.rs · meshing.rs · raycast.rs · brush.rs · placement.rs · the VoxelGeneratorImpl seam (3 adapters) and terrain.rs Reflect types (they are the .terrain.ron schema) · the shape of VoxelWorld (entity-keyed get/set/raycast is the right outward interface) · ChunkTicket · ChunkSaveCompleted/Failed as the outward persistence seam · the server's voxel edit handlers (they use VoxelWorld correctly) · the Nostr/Blossom publish machinery, whose engine contact is confined to the two copies named in candidate 3.

top recommendation

1. Let the Map Instance own its pipeline state

It is the root cause both audits named, and it is the precondition for most of the rest. Candidates 2 and 3 cannot make chunk_levels, dirty_chunks or PendingSaves private until one struct owns them, and candidate 4 needs a single place to read state from. It costs nothing in parallelism because the nine systems are already chained. I would do it first. Then 2 and 3 are mostly moving code behind fields that are now private.

Suggested order: 1 → 2 (+5) → 3, with 4 anywhere since it is independent; its table tests would also protect the other refactors. Record 6 as a decision rather than scheduling it as work.
