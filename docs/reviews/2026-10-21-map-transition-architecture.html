All of the server systems above sit in one unordered add_systems(Update, (...)) tuple (crates/server/src/map/mod.rs:1118-1158). Frame count from request to MapTransitionStart depends on the scheduler's pick. That alone explains why the flow feels nondeterministic.

What the walk turned up (read from source. Items marked verified were traced end to end in a second pass)
  • Returning to a loaded map re-runs preflight. Nothing checks the target's MapLoadState before queueing; configure_map_from_meta then inserts a fresh VoxelMapInstance on the live map entity and sets AwaitingEntities, so saved respawn points are spawned again (preflight.rs:541-570, mod.rs:405-444, 1027-1042). → candidate 1
  • Ready / End messages carry no transition id, and the login path never sets PendingTransition, so a switch request during the initial load is accepted and the client's first Ready completes the second transition (gameplay.rs:545-577, switching.rs:37-43). → candidate 2
  • Spawn points duplicate on disk. validate_respawn_points is gated on "any map Ready", so it spawns a default point for a homebase many frames before that map's saved points load, and the extra point is saved back. At overworld startup the same thing happens or not depending on executor order. The spawn position does not vary today only because every point sits at the default (gameplay.rs:47-50, 149-162, mod.rs:1037-1042). Verified. → candidate 4
  • A dead player can switch maps. Neither the request handler nor the UI checks for RespawnTimer. If the client reports Ready before the timer expires, phase 2 removes the physics disables while the body is still dead, leaving an invisible, collidable corpse on the server for up to four seconds. Verified. → candidate 8
  • One lost packet hangs a transition. If the datagram carrying MapTransitionStart is lost, a new-map chunk on the unordered channel arrives first, the transport acks it, the client drops it as unregistered, and nothing resends it. Loading has no timeout. Verified. It needs loss or reordering, so localhost cannot show it. → candidate 7
  • Abilities are not room-scoped, but it is harmless. ActiveAbility entities get Replicate::to_clients(All) with no MapInstanceId (ability/activation.rs:169-173). Verified that they carry no position or visuals and the client does nothing with a foreign one, so the cost is bandwidth. Projectiles staying on the old map is correct. → candidate 10
  • Blocked switches are never reported to the client, and a disconnect mid-preflight reaches an expect on the sender (preflight.rs:394-400, transition.rs:56-58). → candidate 2
  • Tests do not cross the real interface. The server tests spawn markers in an app with no systems. rooms.rs re-implements the observer instead of registering it. The client test file is a stub pointing at an integration test that does not exist.

Problem
Map readiness and one player's switch intent share a state machine. MapPreflightKind::MapSwitch carries client, player and source map through four preflight stages (types.rs:26-35, preflight.rs:53-200) so that a fourth stage, CommitTransition, can call the transition module (preflight.rs:316-383). The map entity already has MapLoadState, so a task entity and the map both track the same fact. The task entity also spawns the placeholder and then returns None to wait a frame for commands to apply (preflight.rs:385-408). One active preflight at a time (preflight.rs:28-50) means two players switching to different homebases serialise, and a slow remote fetch stalls every switch and every login. Because the queue never consults the target's MapLoadState, a map that is already Ready gets preflighted again and its live VoxelMapInstance replaced.
Solution
Move the preflight stages into MapLoadState::CheckingPersistence on the map entity itself, driven by one system over Query<&mut MapLoadState>. The interface becomes MapRegistry::ensure(map_id) plus a read of MapLoadState. Delete PendingMapPreflights, ActiveMapPreflight, MapPreflightKind, MapPreflightStage::CommitTransition, PendingMapSwitchPreflight, commit_ready_map_preflights, spawn_map_preflight_tasks, clear_pending_switch_marker. Startup overworld and homebase are the same path with different seeds.
Wins
  • locality: persistence decisions in one place
  • deletion test passes: 8 names vanish
  • interface shrinks to ensure + MapLoadState
  • no "wait for commands" stage
  • maps load concurrently, per entity
  • tests: spawn map, step, assert MapLoadState

Problem
The transition module is shallow. commit_map_transition takes ten parameters (transition.rs:14-25) and the caller has to assemble rooms, senders, respawn query and map params before calling it. Phase is implicit in which marker is present. PendingTransition (protocol, both sides) and TransitionPending (server) coexist with near-identical names and the same lifetime. Solution
Replace the markers with one MapTransition component holding an explicit phase. One system advances every player's transition in a fixed order each frame, consuming MapLoadState from candidate 1 and spawn points from candidate 4. Login becomes a transition with no source room. Give MapTransitionStart, Ready and End a transition id so a late Ready cannot complete the wrong transition, and emit a MapTransitionFailed for the Blocked case. PendingTransition stays as the client-visible marker only if the UI still needs it. TransitionPending and TransitionReadySent go. Register the system group .chain() after the map lifecycle system.
Wins
  • locality: every phase in one match
  • deterministic frame count per phase
  • leverage: login and switch share one implementation
  • two markers and one dead marker deleted
  • tests: insert component, step, assert phase + sent messages

Problem
Room membership leaks across the seam. A freeze bundle (RigidBodyDisabled, ColliderDisabled, DisableRollback) can become one Frozen component with its own observers, by the same principle.
Wins
  • locality: one place decides room membership
  • leverage: any entity that changes map just moves
  • no double AddEntity, no silent stale membership
  • RoomEvent never appears outside the module
  • tests: rooms.rs already tests this interface

A SystemParam wrapping the respawn query. No DEFAULT_SPAWN_POS outside it.

Problem
Three different pieces of code answer "where does a player appear". Two callers take the first query match, which is archetype order, not a stable order. With more than one respawn point per map the arrival position changes between runs. The death path ignores the map entirely (gameplay.rs:334-347). Repeat that over save and load cycles and the points pile up.
Solution
One SpawnPoints system param with two methods. Deterministic ordering inside. A missing point is a loud failure since validate_respawn_points guarantees one per map. The three call sites shrink to one call each.
Wins
  • deterministic arrival position
  • death respawn respects the map
  • locality: one fallback policy
  • deletion test: three copies collapse to one
  • tests: table of points in, position out

Problem
Chunk streaming and the transition only agree by timing. push_chunks_to_clients starts the new map's chunks on the frame after commit and resets its sent-set without telling the client to unload the old map. The client drops any chunk for a map it has not registered and the server never resends it. The channels are independent, so the ordering the ApplyDeferred comment defends only holds within one frame. Verified against the vendored lightyear source. Start goes out in frame N, the first new-map chunk in N+1, usually under a millisecond later since the server loop has no frame wait. If the Start datagram is lost, the chunk packet arrives first, the transport acks it at packet level, the client drops the message as unregistered, and the reliable sender never resends it. Start is resent after about 1.5 round trips, by which time the chunk is gone. There is no timeout in Loading and no client-to-server chunk request, so a dropped chunk inside the readiness radius is a permanent hang. Localhost cannot show it because delivery there is in order.
Solution
Make chunk streaming for a client a function of its transition phase. The server streams only when the client has acknowledged the Start, and sends an explicit unload for the old map. Make a chunk the client could not place a loud event, not a silent continue. Tests: a sent-set that resets on map change, and a resend after a reported miss.
Wins
  • no reliance on cross-channel timing
  • no silent chunk drop
  • locality: streaming policy in one module
  • a hung Loading phase has a cause

Shared in protocol, so server and client freeze identically. Candidate 2's state machine inserts and removes one component.

Problem
"Hold this entity still" takes four to six avian and lightyear components to say, and each of six sites chooses a different subset. Transition and death do overlap, verified. Nothing on the switch path checks RespawnTimer, so a dead player can request a switch. If the client reports Ready first, phase 2 strips RigidBodyDisabled and ColliderDisabled while RespawnTimer and zero health remain, and the server has a collidable corpse that eats projectiles and blocks other players for up to four seconds while every client still draws nothing there. If the timer expires first, the server unfreezes the body on the new map while the client is still loading. The Complete phase also removes a marker that is never inserted.
Solution
One Frozen component in protocol with Add and Remove observers that own the physics and rollback components. The transition and respawn modules insert and remove Frozen and nothing else. Overlap becomes explicit, a set of reasons that unfreezes when empty.
Wins
  • locality: physics disables in one observer pair
  • death during a switch has defined behaviour
  • six sites shrink to one insert or remove
  • tests: add Frozen, assert components

9. Name the schedule: an ordered transition system set

Worth exploring in-process
crates/server/src/map/mod.rs:1118-1158 (ServerMapPlugin)

MapSystems::ReceiveRequests

configure_sets(Update, (...).chain()) once; every transition system names its set. Login and switch systems share the sets. The frame count per phase becomes a constant you can assert in a test.

Problem
Order is the interface of a Bevy schedule, and here nobody declared it. The login chain lives in a different plugin with no edge to the map systems. Verified against Bevy 0.18.1: eleven pairs among the transition systems have conflicting access and no edge, the executor picks their order from thread-pool timing, and ambiguity detection is off and never enabled in this repo. What that changes today is smaller than I first claimed. Spawn position does not vary, because every respawn point sits at the default. What varies is whether MapTransitionStart goes out this frame or next, and whether an extra respawn point gets saved to disk at startup. Several "wait a frame for commands" branches exist only because the writer could not say which system runs first. Still the cheapest determinism win on the list, and it survives every other candidate, but it is insurance for the next bug rather than a fix for a current one.
Solution
Turn on ambiguity_detection: LogLevel::Warn for the server Update schedule first, so the list of conflicting pairs comes from Bevy rather than from a reviewer. Then one MapSystems set enum in the server crate, configured as a chain. Each transition system goes in a set. A test runs one update with a request queued and asserts the exact phase reached.
Wins
  • deterministic frames per phase
  • ordering readable in one place
  • "wait for commands" branches become provably dead or provably needed
  • independent of candidates 1 to 8

Problem
Downgraded after verification. ActiveAbility entities do replicate to every client (no NetworkVisibility means lightyear sends to the full Replicate target), but they carry no position or visuals, the client's only consumer fails its caster lookup and does nothing, and they live under two seconds. The cost is bandwidth and a predicted entity per cast. A projectile staying on the caster's old map is correct, since the collision filter is per map and every caster lookup is fallible. The control.rs comment is still wrong during the room gap, but that is candidate 3's problem.
Solution
Add MapInstanceId and NetworkVisibility to the ActiveAbility entity at spawn, which is a two-line change and belongs in housekeeping. The relationship-driven version only earns its slot if abilities ever need to follow a caster across maps, and nothing does today.
Wins
  • bandwidth: casts stop fanning out to every client
  • one fewer opt-in to forget
  • not worth a seam on its own
