Architecture review: filesystem persistence

untitled-brawler · 2026-10-21 · scope: the save directory on disk and the machinery that reads and writes it. git/bevy-persistence, voxel_map_engine/src/persistence/, server/src/persistence/, and the server systems that touch them. The Map Instance itself is covered by the earlier review and is out of scope here.

module seam leak across a seam deep module implementation hidden behind an interface

The verdict. Over-engineered and a ball of mud at the same time, and for one reason. The save directory is a single thing with a fixed layout, and it is modelled as eleven independent generic key-value stores. The generics in bevy-persistence, Store<K,V>, StoreBackend<K,V,B> and PendingStoreOps<K,V>, promise a seam where the backend varies. Nothing varies. Every adapter in the repo is the filesystem, no app-level fake exists, and half the stores are called synchronously through .0 anyway. So callers pay the full cost of the abstraction and get no leverage back. The bill is nine components on one entity, a 14-wide query, five hand-written drain loops and seven copies of tmp-then-rename.

What is already fine. The revision promote / validate / quarantine logic in server/src/persistence/mod.rs:565-1060 is coherent and has about twenty tests. The AsyncStore seam for Blossom and Nostr is a real seam, with three production adapters and two fakes. Neither is touched below.

No CONTEXT.md or ADRs exist. I took the domain nouns from the code: Map Instance, Chunk, Chunk Envelope, Map Meta, Change Set, Revision, Accepted Head, Local Head, Publish Journal, Publish Draft.

A caller that today writes FsAcceptedMapHeadStore { map_dir: Arc::new(dir) }.save(&(), &rev) writes dir.accepted_head().write(&rev). install_active_revision_store_backends becomes dir.activate(), no component churn.

problem
The layout of one directory is spread across nine adapters and four raw-fs sites, and the atomic-write routine is copied seven times. The modules are shallow. Each adapter's interface, meaning its file name, its codec and its version constant, is its whole implementation.
solution
Fold all nine adapters, the two path helpers, the revision naming and the pointer swap into one MapSaveDir with typed slots. One codec, one atomic write, one version check per slot. Staging is the same type pointed at a different root.
wins
  • locality: one layout table
  • locality: one tmp/rename, one version check
  • leverage: ~30 call sites learn one type
  • interface: 9 adapters + 2 helpers → 1 module
  • delete the duplicate EntityFileEnvelope
  • tests: layout round-trips in one file

Deletion test. Delete the nine adapters today and each caller regrows a file-name literal and a tmp/rename. Delete MapSaveDir after the move and all of that regrows in one place. Concentrates.

A SaveJob is a write with a SaveKey and a producer closure, or a delete of a key. The closure builds the Chunk Envelope once, inside the task, when it runs. The queue writes through MapSaveDir, so Store<K,V> and StoreBackend leave the server entirely.

problem
The async-dispatch module is instantiated once per value type. One map therefore carries nine components, every consumer re-writes the poll, drain and forward loop, and three shutdown paths each spawn then flush by hand. None of that machinery hides anything. Every caller sees tasks, completions and errors.
solution
One MapSaveQueue component owning the task list, the per-frame cap, per-key ordering, batches and the blocking flush. One drain system. One message per batch outcome. PendingSaves in the engine becomes a call to enqueue.
wins
  • interface: 9 components → 2
  • locality: 5 drain loops → 1
  • locality: 3 flushes → 1, covering queued and in-flight
  • delete jobs fix the tombstone race where it lives
  • leverage: tests add one component, call flush_blocking
  • delete 40+ .0 unwraps

Deletion test. Delete StoreBackend and nothing concentrates; the .0s just disappear. Pass-through. Delete MapSaveQueue after the move and five drain loops and three flushes regrow. Concentrates.

After this, git/bevy-persistence has one consumer left, the client identity store, which does one load at startup. Decide whether to keep the crate for that or inline a forty-line equivalent. Not a blocker either way.

Three disk reads per cycle, two load state machines at open, a shutdown path that is a second copy of the cycle, and a durability rule that fires on the first file instead of the last.

after · memory first, every write is a job in a batch
publish state · one component per map
PublishState::load(&dir) // once, at open
record_edits(dirty, meta) → bool
open_draft(batch, revision, draft)
commit_batch(batch) → Option<Draft> // local head advances here
abandon_batch(batch) // log, drop, re-dirty
one save cycle, two triggers
save_cycle(map, dirty) // change set, meta, entities, chunks, deletes, draft
debounce timer → save_cycle
AppExit → save_cycle, then queue.flush_blocking()

Reads from disk happen only at open. Drafts are named by revision number and deleted once journaled. Preflight reads meta from the path in one stage.

problem
Three singletons are read, modified and written against disk every cycle, so writes must block to be readable. That rules out one non-blocking write path and leaves the shutdown copy of the cycle to drift, which it has.
solution
Publish state lives on the map entity. Every write is a Save Queue job in a Save Batch. The local head advances when the whole batch lands. Shutdown is the same cycle plus a blocking flush.
wins
  • locality: one save cycle
  • interface: 2 load state machines → 0
  • durability means the whole revision
  • fixes the final-window publish gap
  • fixes draft-id collisions
  • 3 disk reads per cycle → 0

Decisions. Settled with the owner on 2026-10-21 and 2026-10-22, recorded as D1 to D12 in the plan. This candidate now depends on candidate 2 and lands as step three.

One kind of adapter means a hypothetical seam. The repo pays for it in type parameters, bounds and .0 unwraps, and tests still write real files. The seam that does vary, AsyncStore for Blossom and Nostr, is a different trait and is fine.

after · two honest options
(a) Concrete. Recommended first.
MapSaveDir is a plain struct. Tests keep using tempdir, which they already do and which is fast. The generic trait, its bounds and its component wrapper are deleted.
(b) Real seam, only if (a) proves slow or flaky
trait Blobs { read(rel) · write_atomic(rel, bytes) · delete(rel) · list(dir) }
FsBlobsMemBlobs
Layout, codec, versions, staging and promote all sit above the seam and run in memory. Two adapters, so the seam is real.
problem
Store<K,V> was built as a seam for varying backends. Nothing varies, so it is pure cost. It also sits at the wrong level. A fake behind it would have to re-implement the layout, and the layout is the part worth testing.
solution
Drop the trait. If an in-memory adapter is ever wanted, put the seam below the layout at the byte level, where an adapter is ten lines.
wins
  • delete 3 type parameters from every store use
  • a seam placed where an adapter is cheap
  • revision tests could run in memory

Latent bugs the walk exposed

Each one lives in the glue that candidates 1 and 2 would delete. Decide whether to fix first or pin as a test and fix during the move.

server/src/map/mod.rs:873-892 save_dirty_chunks_flush never drains PendingSaves.queue. Chunks evicted into the queue, or left there by the 16-per-frame cap, are not written on shutdown.
server/src/map/mod.rs:924 when is_dirty is false at AppExit, chunk tasks already in flight are never flushed.
server/src/map/mod.rs:661-674 the tombstone cancel filters only the queue. A task already spawned recreates the deleted file. The homebase delete at homebase_publication.rs:316 does not filter the queue at all.
server/src/map/mod.rs:68-81 log_save_errors keeps only completions with an id. Every chunk and chunk-entity completion is id-less, so they are all discarded, and ChunkSaveFailed is logged twice.
server/src/map/mod.rs:274-276 vs 262-273 unpublished/ drafts are rooted at the active revision dir; heads and change set at the canonical dir. A restore silently changes where pending drafts live.
every Fs*Store::save the temp file is path.with_extension("bin.tmp"), fixed per key. Two in-flight writes to the same key share it and corrupt each other. Nothing prevents two spawns for one chunk.
server/src/map/mod.rs:1108 · persistence/mod.rs:414-475 SaveOpIdAllocator restarts at zero each run and draft files are never deleted, so every run's first draft overwrites unpublished/1.bin. An un-journaled draft from the previous run is lost if the process dies before publishing it.

Deep already, leave alone

The revision lifecycle is one coherent module with about twenty tests. That covers materialize_validated_map_save, staging, atomically_promote_staged_revision, pointer validation, quarantine and rollback. It should move behind MapSaveDir as stage / promote but its logic stays as is. MapChangeSet semantics. The AsyncStore seam and its Blossom / Nostr adapters. The publish journal state machine in remote_publish.rs, which is out of scope here.

How this fits the Map Instance review

That review's candidate 3 moves envelope building and the dirty-chunk drain into the Map Instance as instance.flush_dirty(&mut storage), and names a ChunkStorage::for_dir(map_dir) it writes to. Candidates 1 and 2 here are that storage: MapSaveDir is the directory, MapSaveQueue is the async pump. They compose without either review touching the other's internals. The Map Instance hands over (pos, ChunkData) jobs. The queue and directory take it from there. Candidate 3 there can land before or after candidates 1 and 2 here.

top recommendation

1. One module owns the save directory

It is the pure half, with no ECS, no task pool and no frame ordering to reason about. It deletes the most copied code, seven atomic writes, nine file-name literals and a duplicated envelope type. It has the smallest blast radius. And candidate 2 needs it, because a single save queue can only exist once one thing knows how to write any key.
